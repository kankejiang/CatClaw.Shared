### 迁移的代码与兼容策略

1. **JsRuntimeServiceBase**（源自音乐端实现，两端 91.7% 相同）
   - 差异参数化：音乐 =（递归 5000，超时 10s，音乐版文案）；影视 =（递归 2000，超时 60s，通用文案）
   - **接口不下沉**：`IJsRuntimeService` 是插件 SDK 的一部分（LxSource 等插件按"程序集+命名空间+类型名"消费），必须留在各宿主 Core，否则已发布 .ccp 插件二进制不兼容。App 侧改为 `sealed class JsRuntimeService : JsRuntimeServiceBase, 本应用 IJsRuntimeService`，DI 注册与 MauiProgram 零改动
2. **DownloadStatusConverter**（两端逐字节相同）
   - 实现上移共享库；App 内保留同名空子类作为 XAML/C# 兼容占位——`DownloadsPage.xaml`、`Colors.xaml` 的 xmlns 与资源字典**零改动**

## 四、后续演进路线（建议优先级）

1. **P1 — DownloadManager 共享骨架**（最大收益）：抽 `CatClaw.Shared.Core/Downloads/DownloadManagerBase<TItem>`（并发调度、进度聚合、断点续传、通知事件），两端只剩条目模型 + 存储分支。建议单独排期，配基线行为快照测试后再动
2. **P1 — GitHubReleaseClient**：两端 UpdateService 的 GitHub API 查询/版本比较逻辑上移，App 保留各自的"忽略版本/红点"等策略层
3. **P2 — DownloadsViewModelBase**：下载页 VM 的任务列表/过滤/命令骨架
4. **P2 — Windows 平台模板**（App.generated.cs / App.InitializeComponent.fallback.cs / MainApplication.cs）：内容相同但属于 App 入口，上移收益低、风险敏感，可只做同步检查（每次改一边时 diff 另一边）
5. **P3 — 启动诊断日志统一**（StartupLog/DiagLog）、主题基类（IThemeService 公共段）
6. **原则**：共享库内禁止出现品牌名/App 专属文案；差异一律构造参数或抽象成员；Jint/Acornima/MAUI 版本三处同步升级；每次上移先用 `tools/scan_dup.py` 复核相似度
